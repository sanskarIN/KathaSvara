# v0.2.1 — Pronunciation and production reliability

**Status:** experimental, offline-first desktop developer preview. This document describes code contracts, not actual human-verified speech quality.

## Project storage and backwards compatibility

The existing schema version remains `2`. An **optional** `pronunciation_glossary` array contains at most 100 `{id, original, spoken, enabled}` records. Existing v0.2.0 JSON with no glossary loads as an empty list in Python and via Rust `serde(default)`. Rust writes v2 projects under `projects-v2` atomically and never overwrites older `projects/` files when migrating. Both Python and Rust validate supplied glossary records before accepting projects.

A glossary belongs to an individual project and is explicitly reviewed by the user. The original script, the parsed `original_text`, the editable `spoken_text`, and the effective text sent to the synthesis engine are **four different concepts**. The glossary only transforms effective text, not stored script or reviewed dialogue. All stage directions are excluded from synthesis. Character labels do not become spoken material.

## Text matching contract

- Normalize source and matching terms to Unicode NFC; normalize tabs and horizontal whitespace; retain line breaks as paragraph boundaries.
- Match escaped literal terms only, case-insensitively for mixed Hindi/English. No user regex, phoneme language, SSML or recursive replacement.
- Resolve overlapping terms deterministically: prefer the longest original form, then the stable rule ID.
- Require Unicode word/phrase boundaries, including Devanagari marks, nukta, virama, ZWJ and ZWNJ as word constituents.
- Do not match inside a longer word. Disabled rules never apply.
- Reject invalid control characters, blank/duplicate source terms, malformed records, more than 100 rules, or effective speech exceeding 100,000 characters.
- `preview_pronunciation` invokes Python through the same bounded Rust bridge as real rendering; it returns the exact preprocessed text and applied rule IDs **without importing Chatterbox or loading weights**. No preview claims to be audible speech.

## Rendering and cache decisions

The Python render pipeline applies `apply_glossary()` to each speech segment before splitting for synthesis. Cache fingerprints hash **effective normalized text**, current model ID, supported engine parameters and sample rate. Unrelated unchanged effective text therefore retains reusable cached audio when a rule is edited, disabled or deleted. A new cache format/key version (`v=2`) separates these files from previous preview cache keys. The model identifier must be pinned to an exact model revision by operators requiring reproducible audio; an arbitrary label is not proof of identity.

The renderer checks candidate cache WAV format, PCM16 subtype, mono channel count, sample rate and bounded duration, and rereads sample data for finite amplitudes before reuse. Unsafe/corrupt entries are regenerated, not concatenated. Completed good segments survive failure/cancellation for explicit retries, while the combined WAV is finalized atomically only after full success. Cancellation remains **cooperative between chunks** and can take time while model inference is running.

The editor drops combined previews after editing, reparsing, switching documents or unmounting. New renders carry job UUIDs and revision checks; completed results for stale revisions are discarded. Cache entries on disk are content-addressed by effective speech and are not globally deleted on unrelated changes.

## Subprocess resilience

The Windows executable no longer embeds a CI or developer checkout directory. The inference source must be explicitly configured with an absolute `KATHASVARA_INFERENCE_DIR` when outside a source checkout; in development, the bridge discovers the nearest checkout from the runtime working directory. Python stdout is consumed concurrently with a one-megabyte cap and child timeout, preventing a full operating-system pipe from blocking a legitimate parser response. A malformed or oversized response is rejected rather than silently truncated. The plain test remains model-free and does not claim real audio acceptance.

## Security and remaining limitations

Python requests use a bounded JSON bridge; project writes and file exports use the existing Rust commands and OS app-data folder. Export refuses to replace existing files. The Windows candidate EXE remains unsigned, unbundled and requires external Python 3.11 and approved model weights; no weights are distributed. Distinct voices, speaker conditioning, pitch/speed, actual voice quality, and clean-machine Windows startup are unverified. The app's 25 MiB preview bound, 256-segment render cap, 500-chunk cap and 20-minute duration cap remain.

## Deferred beyond this iteration

Fine-grained job state histories and automatic failed-segment scheduling, persistent render manifest, bounded cache eviction, full scene-by-scene export, advanced human listening acceptance and verified clean-Windows dependencies require additional implementation and tests. A user can explicitly render or force-retry a **single selected spoken segment**, without concatenating its neighbors; partial automatically recovered story output is not silently exported.
