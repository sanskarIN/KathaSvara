# KathaSvara v0.5.0 — Model-free per-scene production audit (development)

**Status:** active development only. No v0.5.0 tag or executable release has been published. The preceding [v0.4.2 experimental pre-release has now been published](https://github.com/sanskarIN/KathaSvara/releases/tag/v0.4.2) and its [exact-SHA release workflow passed](https://github.com/sanskarIN/KathaSvara/actions/runs/39540443967). This work remains unreleased v0.5.0 development.

## New capabilities in this batch

- Add **Audit scene readiness (no model)** to Characters & Scenes. In one inspection, see whether each scene can begin a Hindi dialogue render with existing character assignments and pronunciation controls, plus whether the combined story meets the whole-render limits.
- Share validation with the existing trusted, model-free `prepare_render_plan`. Each scene is checked independently, so a missing speaker in one scene does not disguise a valid independent scene.
- Report count-only readiness results and **fixed reason codes**: `ready`, `no_dialogue`, `unassigned_speaker`, `over_limit` and `needs_review`. The IPC JSON report does not include story text, pronunciation substitutions, character names, voice parameters or scene titles. The React view locally associates scene IDs with existing labels.
- Distinguish a project containing individually renderable scenes from one too large to render as a single 20-minute/256-line job. No actual audio duration can be predicted.
- Add mock/model-free Python tests for valid scenes, unknown speakers, stage directions, empty stories, per-scene vs full-story limits, strict payload validation and privacy of response data.
- Wire the audit through Python CLI -> Rust/Tauri command -> React, with stale-result invalidation on project changes and a clear warning that synthetic voice quality has not been verified.

## Privacy-safe production manifest export

- A completed model-free scene audit now exposes **Export privacy-safe audit JSON** as an explicit user action. The app never silently uploads a report or records it to disk.
- The exported JSON schema `kathasvara-production-audit` (schema v1) includes only: an explicit `model-free-script-structure-only` assessment label, sequential **scene numbers**, readiness booleans, fixed safe reason codes, speech-line counts, planned chunk counts and `false` flags for loaded model/audio verification/verified distinct voices.
- The export **excludes** original and reviewed Hindi script, scene titles/IDs, story identifiers, character/speaker names and IDs, voice-profile parameters, model paths, cache keys, recordings and generated WAV paths. A user can inspect the JSON before independently deciding whether to share it; any counts and structural indicators may still be sensitive.
- React reconstructs the document from allowed fields only and validates report integrity before opening the native save dialog. Rust separately deserializes a strict JSON schema with **unknown-field rejection**, bounded integer values, fixed reason-code vocabulary, scene-order integrity and false voice/audio-acceptance flags.
- Native export uses an absolute `.json` path and exclusive create-new behavior. It cannot silently overwrite existing JSON reports or symlink destinations. Reports are limited to 64 KB; a failed write removes its own partial destination.
- Vitest and Rust regression tests cover data minimization, forged claims, mismatched counts, file-exists refusal and extension validation. **These tests do not establish actual recorded Hindi voice quality or clean Windows installation.**

## Manual recovery and narration review controls

- **Explicit recovery action:** the Recent render history panel now offers **Retry current full story** only for a bounded, matching-story `interrupted`, `failed` or `cancelled` record. It always requests confirmation, generates a new job UUID and revalidates the **current entire story** against the current voice settings. Existing recovery journals, completed WAVs and exports are not overwritten. Matching content-addressed cached segments may be reused, but this does **not** reconstruct or promise to resume the original scene/line selection: legacy journals deliberately did not persist that scope or story text.
- **Per-WAV human QA checklist:** after a successful render the Characters & Scenes editor shows four opt-in checkboxes for listening through the WAV, reviewing Hindi pronunciation/mixed-language words, checking character turn order and reviewing exported SRT captions. Marking captions reviewed is disabled until this same WAV has successfully exported an SRT. Exporting captions alone marks **no** human QA item.
- Every new generation, story edit/document switch, or audio discard clears/replaces checklist state. The checklist is **in memory only**, not persisted or attached to WAVs, journals, audit JSON, or GitHub releases. Neither the UI nor automated tests claim that a checked box proves real Chatterbox quality or distinct speaker identity.
- The reviewed SRT export now invalidates an in-progress file-selection dialog if the underlying story changes, instead of approving subtitles derived from an obsolete edit.
- Added model-free Vitest tests for new-audio reset, SRT-export prerequisite, explicit unchecked default, progress reversibility, matching-document history checks and corrupt/out-of-range recovery records. Existing cache-reuse and incomplete-journal tests remain in Python.

## Scope-aware WAV/SRT exports and stale-dialog safety

- Capture the export scope **when rendering starts** (full story, selected scene or one selected dialogue line). For a successful WAV, `Export WAV` and `Export dialogue SRT` now suggest the *same filename stem*, including the project title and stable scene/line order as it existed during the render. Navigating to another scene tab later cannot change the generated audio's export label.
- Suggested filenames retain valid Hindi/Unicode letters and marks, but strip Windows path separators, control characters and bidirectional formatting overrides; segment names are length-bounded and may fall back to `story` or `untitled`. These are only suggested leaf filenames, not trusted filesystem paths. The native exporters continue to require absolute destinations and refuse to overwrite existing exports.
- An asynchronous file dialog is bound to the source WAV ID, a generation epoch, and the document revision. If another rendering begins, the audio is cleared, or the document changes while a dialog is open, the **stale export is refused** before writing and never sets human subtitle-review state.
- Existing measured SRT cue text/timings, external Python/model setup, and privacy-preserving production audit remain unchanged. Frontend regression tests cover matching WAV/SRT names, full/scene/line scopes, Unicode and filename traversal safety, missing scope IDs, immutability, and stale-dialog guards.
- No automatic batch-export, ZIP packaging or story audio-quality certification is claimed in this batch.

## Automated desktop controls and real-model acceptance evidence

- Add **Vitest + jsdom + React Testing Library** component-level desktop interaction tests. The checks click production audit and its count-only JSON export, generate a selected-scene WAV using a **mocked** Tauri bridge, export paired WAV/SRT captions, inspect review-checkbox gating, refuse stale dialogs when clearing audio, and explicitly confirm/cancel a recovery retry. These are real React state and event tests but **not** genuine Windows WebView2 sessions or Hindi model synthesis.
- Use mocked inference data only; no model checkpoints, voice samples, machine identifiers or private stories are collected. Successful mock behavior must never be reported as real voice quality.
- Add [a reproducible Windows/Hindi narration acceptance checklist](../qa/windows-hindi-acceptance.md) covering release hash verification, user-authorized Python/model setup, exact click-by-click desktop QA, manually listened Hindi/pronunciation and distinct-character checks, long-form WAV/SRT validation and privacy-limited evidence. **All manual pass/fail results remain unset** until a person actually conducts and records them.
- Extend the normal frontend CI to include this component test suite on every PR; mock tests are labelled as such to distinguish them from clean-machine audio acceptance.

## Conservative offline WAV level hints

- Extend the model-free, standard-library WAV inspector with bounded streaming `peak_dbfs`, `rms_dbfs`, percentage of full-scale PCM16 samples, and two **advisory** booleans for RMS ≤ -60 dBFS (quiet/silent) or at least 1% saturated samples (possible clipping).
- The statistics do **not** use network, GPU, model weights, additional audio copies or script text; maximum per-block PCM memory stays bounded at 8192 samples. Include explicit `false` values for automatic Hindi-listening and distinct-voice verification, even when the PCM levels look plausible.
- Tests exercise synthesized test-data silence, nonzero quiet signal, normal amplitude, full-scale clipping including negative PCM16 saturation, chunk-boundary accumulation and privacy-safe JSON. Thresholds are heuristic, not validated speech-quality metrics.
- See [offline WAV inspection](../qa/offline-wav-inspection.md) and the [manual acceptance protocol](../qa/windows-hindi-acceptance.md) before publishing any release.

## Remaining work toward a broader v0.5.0 milestone

- Extend production planning with per-scene export naming and reproducible opt-in model/hardware details **without automatically collecting sensitive recordings or prompt content**.
- Expand **real Windows WebView2** end-to-end interaction testing with an installed local model and user-authorized weights. The new jsdom component tests cover core mocked UI flows but cannot prove a clean-machine launch.
- Extend the audit manifest with *optional, explicitly consented* QA checklist statuses without exposing text or implying verified model/audio behavior.
- Verify actual Chatterbox multilingual Hindi inference and clean Windows setup before any stable release; tracked in [issue #3](https://github.com/sanskarIN/KathaSvara/issues/3).

## Guardrails

- No model weights, generated voice samples, distinct-character speech promise, automatic resumable rendering, installer or signed binary in this development batch.
- A model-free readiness report is a **script structure and render-limit check**, not proof of TTS installation, human-approved captions or natural Hindi pronunciation.
