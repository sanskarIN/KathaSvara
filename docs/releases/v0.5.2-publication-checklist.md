# KathaSvara v0.5.2 — operator checklist for a one-time experimental pre-release

**Status:** Instructions only; **not proof that v0.5.2 has been published**. The published pre-release must be confirmed via the GitHub Release API, a matching immutable tag, and three verified assets. **This is not a stable or self-contained Windows installer.**

## 1. Confirm the exact candidate

On the [repository main branch](https://github.com/sanskarIN/KathaSvara/tree/main), copy the **full 40-character hexadecimal commit SHA** at the tip of `main`. Do **not** copy a PR head or an earlier successful CI SHA.

- [ ] All intended v0.5.2 changes, regression tests and documentation are merged; no unfinished blocking PR.
- [ ] The standard [KathaSvara CI](https://github.com/sanskarIN/KathaSvara/actions/workflows/ci.yml) finished successfully for **that same SHA**, including Python, React, Windows Rust/Clippy and model-free Windows Python tests.
- [ ] The tag `v0.5.2` does not yet exist and there is no existing `v0.5.2` release. **Never overwrite or retag** a published version.
- [ ] `apps/desktop/package.json`, the npm lockfile, Cargo manifest, Tauri JSON and Python project manifest all identify `0.5.2`.
- [ ] The operator has read [draft release notes](v0.5.2-notes.md), [Windows developer prerequisites](../installation/portable-windows-candidate.md) and [manual acceptance issue #3](https://github.com/sanskarIN/KathaSvara/issues/3).
- [ ] Any known limitations are honestly stated: unsigned Windows executable, Python 3.11 and Chatterbox dependencies/approved model weights **not bundled**, and real Hindi naturalness/clean-Windows launch **not verified**.

Successful CI confirms code-level gates, **not** genuine narrator audio, source licensing, a supported installer or distinct-character voices. If this is a stable release candidate, stop: issue #3 requires actual manual evidence first.

## 2. Dispatch the guarded workflow intentionally

A repository maintainer signed in to GitHub can open:

[Actions → Publish KathaSvara v0.5.2 experimental subtitle and recovery prerelease](https://github.com/sanskarIN/KathaSvara/actions/workflows/release-v0.5.2.yml)

1. Choose **Run workflow**.
2. Select branch **main**.
3. Paste the **exact full SHA of current main** into `release_sha`.
4. Start the workflow **once**. Do not use the older v0.5.1 release workflow, a commit from a PR branch, or a shortened SHA.
5. Verify that the `prepare` gate succeeded: it rejects a stale main SHA, malformed SHA, existing tag and existing release. The workflow is intentionally `workflow_dispatch`-only, so a branch push or PR merge must **not** publish.
6. Monitor `python`, `frontend`, `rust-windows`, `windows-python-lock`, `windows-exe` and finally `publish`. A failed, skipped or cancelled mandatory gate means **no release success**.
7. Before the publish job uploads anything, it rechecks that `main` still points to the originally tested SHA. If main advanced, do **not** bypass the check: review the new commit and rerun at the new SHA.

The test EXE is compiled on a Windows GitHub runner at the exact candidate commit, without a bundled installer or speech model. The workflow cannot conduct actual human Hindi listening.

## 3. Verify publication and the downloaded Windows artifact

Only after the whole workflow is green, open the exact release at:
https://github.com/sanskarIN/KathaSvara/releases/tag/v0.5.2

- [ ] The release exists, is labeled **Pre-release** (not a stable release), and its target tag resolves to the dispatched SHA.
- [ ] Exactly three release assets are present: `KathaSvara-v0.5.2-dev-win64.exe`, `README.txt` and `SHA256SUMS.txt`.
- [ ] `README.txt` states **NOT A COMPLETE INSTALLER**, lists Python 3.11, discloses model/weight prerequisites and does not promise verified voices.
- [ ] The downloaded EXE SHA-256 matches the digest listed in the release's `SHA256SUMS.txt`.
- [ ] No unexpected tag edits, duplicate release assets or silently replaced files are present.

For example, in PowerShell inside the directory containing your downloaded release files:

```powershell
Get-FileHash -Algorithm SHA256 .\KathaSvara-v0.5.2-dev-win64.exe
Get-Content .\SHA256SUMS.txt
```

Compare the hexadecimal digest and exact filename manually. The release workflow also downloads all three published assets and verifies the checksum automatically. **Do not disable Windows security protections or bypass an untrusted-download warning** just to complete this test.

## 4. Keep website and release status truthful

- [ ] **Only after verified publication**, update the website's latest-release CTA and version text from `v0.5.1` to `v0.5.2`; update its regression test to the actually published version in a separate checked PR.
- [ ] Keep historic release links unchanged; do not falsely claim the source-only preview was available in the previously published v0.5.1 binary.
- [ ] Keep the real-Hindi and clean-Windows [acceptance issue #3](https://github.com/sanskarIN/KathaSvara/issues/3) open. Passing tests cannot check manual listening.
- [ ] After publication, add v0.5.2 to the published-workflow policy tests and retain its **manual-only**, immutable-tag gates; do not add a new automatic trigger to an already published workflow.
- [ ] Provide honest social announcements: experimental unsigned developer executable, no bundled Python/model, segment-level (not word-level) subtitle timings, and explicit listening/Windows limitations.

If publication cannot be initiated because no GitHub account is authenticated or no authorized workflow-dispatch tool is available, **leave the tag and release untouched**. Hand these instructions to an authorized maintainer rather than weakening the workflow.

## 5. Separate human acceptance

Use the original [Hindi dialogue fixture and blank listening matrix](../qa/hindi-manual-listening-fixture.md) and the [Windows/Hindi acceptance protocol](../qa/windows-hindi-acceptance.md) on authorized model weights and a real Windows machine. No pre-release approval, publication, or synthetic WAV test should automatically change those blank outcomes.

**Operational decision:** If the workflow is green and the GitHub prerelease assets are intact, v0.5.2 may be labeled an **experimental developer pre-release only**. Otherwise report `not published / blocked`, never success.
