# KathaSvara v0.5.2 development — local Hindi subtitle cue review

**Status: source development only.** No v0.5.2 release, installers, signed executables, or real-Hindi listening verification are claimed by this change. The latest published version remains [v0.5.1](https://github.com/sanskarIN/KathaSvara/releases/tag/v0.5.1).

## Creator workflow

1. In **Characters & Scenes**, generate a scene or story dialogue WAV using the configured local inference environment.
2. Choose **Preview dialogue cues** to inspect the full set of measured dialogue timing entries. The first ten cues are shown; Previous/Next controls page through up to 256 cues.
3. Compare Hindi caption text and measured timestamps with the audio. When the WAV fits the 25 MiB inline-preview limit, use **Jump to cue** to seek the player. For longer export-only recordings, open the WAV in a local audio player instead.
4. After personally checking, use **Export dialogue SRT** to create a new `.srt` file. This separate action must succeed before the manual subtitle-review checkbox can be marked.

The preview is session-only and cleared when the document, active audio or render session changes. It makes no IPC request and writes no local preview files.

## Correctness and privacy boundaries

- **One canonical validator:** preview and export use the same rounded-millisecond cue construction. Both reject zero-duration, overlapping, non-finite, negative, beyond-20-minute or missing-caption timelines.
- **Render-time text wins:** captured glossary-adjusted `effective_text` is used ahead of later source-dialogue edits. Whitespace is normalized and unsupported control characters are rejected.
- **Duplicate cue protection:** each generated segment identifier must appear only once.
- **Whole-output validation:** every cue is validated even when previewing only page one.
- **Story ownership and media bounds (post-preview refinement):** every subtitle segment must exist in the current story even when a render-time text field is present. Both preview and export reject cues whose rounded endpoint exceeds the reported WAV length by more than the small five-millisecond metadata tolerance, and reject invalid sample-rate/duration metadata.
- **On-device search (post-preview refinement):** creators can search up to 120 characters of Hindi/other subtitle text within the validated cue set. Matching cues keep original SRT numbers; pagination resets when the query changes. Filtering only changes the on-screen view, never the exported complete SRT or manual review status.
- **No false approvals:** displaying cues does not generate audio, export captions, satisfy listening acceptance, certify voice distinctness or advance the manual QA checklist.
- **Bounded UI:** ten cues appear per page; the review is restricted to the active generated audio identity.

## Inline preview read integrity

Inline playback now reads at most 25 MiB from the **same opened WAV handle** that passed the native RIFF/PCM16 inspection rather than reopening a pathname between validation and Base64 encoding. The reader verifies length and opened-file modification metadata against the snapshot taken before validation, and refuses files that grow, truncate or change during preview loading. Longer WAVs remain export-only. These checks reduce accidental and common concurrent-file races but do not provide an adversarially immutable filesystem snapshot or human audio acceptance.

## WAV-header and render metadata integrity

The native RIFF/PCM16 reader now provides verified frame count, sample rate and bounded byte size from an opened WAV. The desktop compares these facts with the Python worker's reported output duration and rate before offering preview/export, rejecting contradictory metadata (up to 5 milliseconds of rounding tolerance for duration). Previously a structurally valid WAV paired with inconsistent JSON timing could be accepted. This only tests file metadata consistency; it is not a listening pass or cryptographic snapshot.

## Native subtitle validation consistency

The Rust bridge now enforces the same millisecond-rounded, monotonically ordered subtitle boundaries before returning rendered metadata to React. It also rejects duplicate dialogue IDs, unsupported control characters and individual captions beyond 3,000 Unicode scalar values. New tests cover a tiny float overlap that becomes a real SRT collision, submillisecond zero-length cues, duplicate IDs and Hindi lines containing legitimate whitespace. This closes a mismatch between native metadata acceptance and the stricter in-app SRT exporter; it does not certify word-level alignment or real speech.

## Editor IPC consistency across story changes

A pending parse, save or load response must not replace a newer script after the user edits or changes stories. The desktop now checks its active document revision before applying these results or claiming a saved/loaded outcome, and suppresses obsolete render errors and production-manifest export messages. These guards protect the user interface; a previously initiated save **may still have written its original document** and cannot be retroactively cancelled by a React check. Tests simulate late results, document switches and stale errors using mocked local Tauri IPC only.

## Verification

The no-model CI suite adds unit checks for rendered Hindi caption agreement, exact millisecond rounding, glossary-adjusted text, duplicate identities, rejected control characters, and an invalid last-page cue. Mocked-Tauri React integration tests exercise the preview button, local seeking, on-device search and paging across more than ten cues, absence of export IPC, unchanged review eligibility, clearing the preview, and refusal of malformed or out-of-WAV metadata.

Run locally:

```powershell
cd apps/desktop
npm ci
npm test
npm run build
```

These checks do not validate spoken Hindi quality, actual Chatterbox voices, subtitle playback in a video player, Windows installation, or model/weights setup. Record manual Hindi and clean Windows observations in [acceptance issue #3](https://github.com/sanskarIN/KathaSvara/issues/3) before considering a stable release.
