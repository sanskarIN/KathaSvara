**कथास्वर — Give Every Story a Voice.**

## Changes planned since v0.5.2

- **Speech startup recovery:** the opt-in `KATHASVARA_TTS_DEVICE=cpu` setting bypasses failing CUDA/MPS capability probes, while `auto` retains the ordinary GPU-first device selection. The Windows source helper supports `-CpuOnly`. CPU mode needs a compatible Python/PyTorch installation and approved model weights; no performance or audible-output guarantee is made.
- **Safer native dependency failures:** Python, Torch, SoundFile and Chatterbox startup failures are converted to privacy-safe diagnostic hints. Raw OS exception text, private paths and tokens are not intentionally forwarded through the desktop JSON bridge.
- **WAV validation, not fake voice acceptance:** model-free tests reject empty, nonfinite, implausibly loud and effectively silent speech chunks. The separately opt-in `scripts/smoke_hindi.py` checks the real-model WAV's PCM16 structure, sample rate, duration and near-silent level, and streams its SHA-256 without reading the entire WAV into RAM. It does **not** listen or verify Hindi pronunciation.
- **Incomplete audio cleanup:** if a native WAV library fails after creating a temporary output or throws while closing a partial file, the streaming writer now attempts immediate cleanup instead of stranding an invalid file. Model-free failure-injection tests exercise both paths. Exclusive-create collisions with another process are now explicitly preserved instead of deleting the pre-existing temporary file (including symlinks); synthetic race and collision tests protect the no-overwrite contract.
- **Reliable dialogue composition:** zero-millisecond speaker pauses do not attempt empty writes; inter-speaker pauses and incremental chunk lengths are included in the 20-minute PCM frame budget *before* expensive audio concatenation. Valid short/zero pauses and over-budget handling have regression coverage.
- **Caching and recovery:** corrupt or effectively silent cached segments are rejected and can be regenerated. Cache reuse does not establish that the generated voice sounds natural or that separate characters have distinct voice identities.
- **Scene and character editing:** the v0.5.3 development branch includes deterministic dialogue-line ordering and source-preserving scene/character editor safeguards. Stage directions are not synthesized as speech. Source-only and mocked desktop tests check selection, edits and document integrity, but not genuine Windows interaction or narration.

After publication, verify all three uploaded assets, the prerelease flag, exact immutable tag/commit and the downloaded checksum.

## Real local inference is separately configured

The developer EXE does **not** bundle Python 3.11, Chatterbox, PyTorch, third-party voice models, checkpoints, a compatible GPU driver, a voice catalog, or a managed installer. Use an authorized model/weights revision and a configured local Python environment; consult [audio troubleshooting](../installation/audio-troubleshooting.md) and [the Windows developer setup](../installation/development.md). Real model downloads are opt-in and subject to upstream terms.

The actual purpose of the generator is **audible Hindi narrated WAV speech**, followed by reviewed scene dialogue, manual speaker attribution and subtitle export. Compilation, import probes, synthetic PCM tests, and structural WAV inspection are not proof of that goal.

## Remaining acceptance gates

- **Real Hindi quality:** human listening to a genuine licensed Chatterbox run, including pronunciation, mixed Hindi/English words, long-form passages, silence/clipping, and narrator–character turns.
- **Distinct voices:** multiple cast names and adjustable parameters do not establish unique, independently conditioned voice identities. Do not advertise verified multi-voice output.
- **Clean Windows acceptance:** test actual launch, source/Python configuration, audio preview, save/reload, cancellation, cache, SRT and WAV export, and trust prompts on a clean supported machine.
- **Release ordering:** publish/verify experimental v0.5.2 first; merge and revalidate the complete v0.5.3 development work only after the protected v0.5.2 exact-SHA workflow has finished. Run v0.5.3 publication from its **final tested main SHA** through the separately gated manual workflow. Never rewrite an older tag or change the historic v0.5.2 workflow.
