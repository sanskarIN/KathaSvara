# KathaSvara v0.4.1 — Long-render export and subtitle fidelity (development)

**Status:** development batches merged through PR #16; additional safe temporary-file cleanup is under review on `dev/v0.4.1-safe-abandoned-temp-cleanup`. This is **not a published GitHub release**. The latest verified release remains [v0.4.0 experimental](https://github.com/sanskarIN/KathaSvara/releases/tag/v0.4.0).

## Changes in this development batch

### Preserve valid long WAV recordings

- A completed narration WAV larger than the existing **25 MiB browser inline-preview cap** is now retained in the app-data audio directory rather than deleted and reported as a failed synthesis.
- The desktop returns `preview_available=false` and the file byte count, displays a clear **export-only** explanation, and offers **Export WAV** without attempting a very large base64 transfer to the React webview.
- WAV export uses a streaming filesystem copy into a **new file only**. The full audio is no longer loaded into the Rust process as a single `Vec<u8>` during export. An interrupted export removes its partial destination.
- Native checks parse RIFF/WAVE chunk headers and validate mono 16-bit PCM, sample rate 8–192 kHz, exact container size, bounded chunk count, and an audio duration not exceeding 20 minutes **without reading sample data into memory**. Files over **512 MiB** are rejected. This is a local-file validation guard, not a full audio-quality assessment.
- Small WAVs remain playable in the embedded audio widget via the same 25 MiB browser transport; no new audio streaming protocol is claimed.
- New Rust regression tests cover valid long simulated PCM files, no-overwrite export, invalid/truncated headers, and rewind behavior.

### Subtitles match the recorded speech text

- Each generated segment's temporary IPC metadata now carries `effective_text`: the exact reviewed text **after the project's enabled pronunciation glossary rules** have been applied, as used for model synthesis.
- The SRT formatter prioritizes the captured text over any later-edited source document text. This prevents exporting obviously stale subtitles for existing audio when reviewed or glossary text differs.
- Audio metadata carrying text lives in application memory for the preview/export flow. The persistent recovery journal continues to record only safe progress fields, **never story text or the effective subtitle text**.
- New Python/Vitest tests cover glossary-driven subtitle text, caption snapshots and privacy.

## Subtitle export bugfix and WAV post-processing cleanup

- Fix a release-blocking Rust SRT-export bug carried forward from v0.4.0: the native validator matched literal backslash-escaped `\\n` text, while the React subtitle builder emits actual newlines. Valid SRT exports were therefore rejected. The native path now accepts actual line-delimited SubRip text and structurally validates each numbered cue, `HH:MM:SS,mmm` timing, dialogue line, ordering and duration **before creating a file**.
- React and native SRT validation now both check the timestamps **after rounding to integer milliseconds**. Invalid, zero-length, out-of-order, or overlapping captions are rejected consistently.
- If the Python worker completed a WAV but returned missing/inconsistent metadata (including caption timing, duration or chunk count), native cleanup removes that job's unaccepted output instead of leaving an orphan file in the app-data audio directory.
- Regression tests exercise real Hindi text/newlines, escaped literal `\\n`, empty and malformed cues, out-of-range timestamps, overlap and no-overwrite behavior, plus post-render metadata validation and orphan-WAV cleanup.
- These are **engineering validation checks only**, not proof of natural model speech, clean-machine playback, verified character voices, or human-approved subtitle alignment.

## Explicit cleanup for abandoned partial WAVs

- After a crash or terminated inference worker, the streaming WAV composer or content-addressed segment writer can leave precisely named `*.partial.wav` files. The Settings page now offers **Preview abandoned WAV cleanup**, followed by an explicit confirmation button; there is **no automatic deletion**.
- Only files with generated UUID/UUID partial names directly inside app-data `audio/`, or SHA-256/UUID partial names directly inside `segment-cache/`, become eligible **after 24 hours**. A dry run reports counts and disk space without deleting anything.
- Real deletion holds the same **OS-managed advisory cache lock** used by updated narration workers; the Rust bridge additionally refuses maintenance during active same-process renders. The operation refuses symlinked target folders, ignores symlinked files, rechecks inode/size/mtime immediately before deleting and is bounded to 20,000 scanned entries and 1,024 deletions per request.
- Completed `UUID.wav` narration, finished `SHA256.wav` cache, project files, recovery manifests, output exports and other files are intentionally out of scope. No stale journal entries are removed by this operation.
- Dry-run output is an estimate; a file changing after the preview can be skipped in the confirmed pass. Do not manually delete `.kathasvara-cache-operation.lock`; it is intentionally retained for cross-process consistency.
- Model-free regression tests verify stale-file selection and preservation of genuine outputs. Testing does not prove real Hindi speech, an installer or clean-machine playback.

## Recovery maintenance hardening

- The v0.4.1 `abandoned_wav_cleanup` filename filter now matches the actual temporary output patterns used by both WAV writers: `<job-uuid>-<uuid4-hex>.partial.wav` in `audio/` and `<sha256>-<uuid4-hex>.partial.wav` in `segment-cache/`. It does not match arbitrary user WAVs or a second hyphenated UUID suffix. The prior implementation could falsely report zero eligible files because the tests used the wrong naming pattern.
- The maintenance operation now first verifies both directories and completes the entire **20,000-entry bounded scan before deleting any file**, so a symlinked folder or scanning error does not cause a partially applied deletion plan. It still excludes fresh files, symlinks, final WAVs, unrelated names and active participating workers, and caps confirmed deletion to 1,024 files per run.
- Explicitly choosing **Forget record** for an inactive job now checks and deletes only that same job UUID's small `.progress.json` and `.cancel` sidecars as well as its render journal. Unexpected file types or oversized sidecars block forgetting; completed audio, story documents, speech cache and other jobs' files remain untouched.
- Tests use filenames produced by `StreamingWav` directly, preserve unsupported suffixes, verify scanner-failure and symlink preflight leave files untouched, and check that malformed job sidecars cannot remove their journal.
- This remains **developer-stage maintenance**, not a verified automatic crash-resume mechanism or cross-process active-journal detector. Do not use it as evidence of real Hindi narration quality or clean Windows installation.

## Known limits and release gating

- Native WAV export and the experimental SRT feature do not establish that a real Chatterbox model has produced natural Hindi narration or separate actors' voices.
- The 20-minute/256-spoken-segment/100,000-character limits still apply, including the speech engine's own GPU/CPU/memory limits.
- For WAV files above 25 MiB, audio must be exported and played externally; there is **no embedded playback** for these files. The user should verify the exported audio and subtitles.
- No bundled Python runtime, Chatterbox model weights, signed installer or supported clean-machine Windows setup yet.
- **Do not publish v0.4.1** without reviewing full Python Ruff/pytest, React/Vitest/TS build, Windows Rust tests/Clippy, and Windows EXE candidate checks, plus the manual acceptance still open in [issue #3](https://github.com/sanskarIN/KathaSvara/issues/3).
